## Detecting Existing Changesets

Check for pending changesets first:

```bash
ls .changeset/*.md 2>/dev/null | grep -v README.md
```

If any exist, ask the user whether to create an additional one or skip.

## Creating a Changeset

Prefer non-interactive creation for agent mode:

```bash
# Interactive (TTY required)
npm run changeset

# Non-interactive: write the changeset file directly
cat > .changeset/<short-id>.md << 'EOF'
---
"<package-name>": patch
---

<description of changes>
EOF
```

Generate the short id: `node -e "console.log(Math.random().toString(36).slice(2,10))"`.

### Bump Type Selection

| Type  | When to use |
|-------|-------------|
| patch | Bug fixes, documentation, internal refactors (default) |
| minor | New features, non-breaking additions |
| major | Breaking changes (only with explicit user instruction) |

Default to `patch` unless the user specifies otherwise.

### Changeset Summary

Infer the summary from recent commits:

```bash
git log --oneline -10
```

Write a concise 1-2 sentence description of user-facing changes.

## Quality Gates

Run quality checks in this order before committing. Discover scripts first:

```bash
cat package.json | jq '.scripts | keys[]' -r
```

### Gate Order

1. **Lint:** `npm run lint` or the project's lint script
   - Auto-fix: `npm run lint -- --fix` or `npx eslint --fix <changed-paths>`
2. **Type-check:** `npm run typecheck` or `npx tsc --noEmit`
   - Fix manually; no safe auto-fixer
3. **Tests:** `npm test` or `npm run test`
   - Fix failing tests; never skip or delete them to get green
4. **Format:** `npm run format` or `npx prettier --write <changed-paths>`
   - Scope to changed files; project-wide formatting hits files outside the change

After any auto-fixer, check `git status` and `git restore <path>` any files it touched outside your change.

### Retry Logic

- Retry each gate up to 5 fix iterations; report the remaining error count each pass.
- If a gate still fails after 5 iterations, stop and report to the user.
- Re-run all gates from the start after any code change to catch regressions a fix introduces in an earlier gate.

## What Happens Next (CI Handles Versioning)

After the changeset file is committed and pushed, CI's `changesets/action` detects the pending changeset on the default branch and opens (or updates) a "Version Packages" PR on branch `changeset-release/main`, containing the `package.json` bump and `CHANGELOG.md` updates generated by `changeset version` in CI.

**Do not run `npx changeset version` locally.** It consumes the changeset file, so the pushed commit has no pending changeset, CI's "Changeset Status" check fails, and no Version Packages PR opens.

The local job ends at "commit + push the changeset file".

## Commit and Push

Commit message convention: `chore: add <type> changeset for <package>`.

Stage explicit paths (`git add <paths>`, never `git add -A`): pre-commit hooks emit stray artifacts (e.g. a root `schema.gql`) that broad staging silently commits into the release.
