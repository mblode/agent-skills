# Bot Patterns

Detection markers, severity mapping, merge gates, and noise markers for PR review bots. These tables are a shortcut for stripping boilerplate and mapping `severityHints`; they are not an allowlist of who counts.

## Unlisted reviewers

Any author not listed here, bot or human, is an active reviewer and every inline comment is read in full:

1. Each inline comment is a finding at Major unless its own text says otherwise.
2. Severity from whatever the body carries: a bold `**<Word> Severity**` line, a `P1`/`P2`/`P3` or `high`/`medium`/`low` token (including inside a badge image URL), a coloured circle emoji, or the words critical, blocker, major, minor, nit.
3. Strip HTML comments, `<details>` blocks, `<sup>`/`<sub>` footers, link-image lines ("Fix in ...", "Open in ..."), `Reviewed by ... for commit <sha>` footers, "Comment `@x review`" invitations, "Was this helpful?" prompts. What survives is the finding.
4. Label it `unlisted reviewer: <login>` in the report so it can be added here.

A bot listed below as noise or check-only that posts an inline review comment is a stale row: triage the comment on its content and flag the drift.

## Tiers

Classify by content first, then login. A `[bot]` suffix and GraphQL `__typename == "Bot"` are hints: machine users such as `developer-platform-actions` are plain `User` logins, and `github-actions[bot]` is shared by unrelated workflows.

| Tier | Behaviour | Action |
|------|-----------|--------|
| Active reviewer | Findings with severity or actionable suggestions | Triage |
| Merge gate | A verdict on whether the PR may merge | Record for readiness; never fix, reply, or resolve |
| Noise | Linkbacks, deploy status, CI notices, rate limits | Ignore, on a positive marker match only |
| Check-only | In `gh pr checks`, no comments yet | Skip while that holds |

## Active review bots

For every bot here the findings live in the inline comments; the review body is a count or summary. Never conclude a bot found nothing from its body.

| Bot | Detection | Severity | Strip or note |
|-----|-----------|----------|---------------|
| Codex (`chatgpt-codex-connector[bot]`) | Body has `### 💡 Codex Review`; inline comments open with a shields.io badge | `P1` Critical, `P2` Major, `P3` Minor, no badge Major | Badge and `<sub>` wrappers, the "About Codex" `<details>` |
| Devin (`devin-ai-integration[bot]`) | Inline comments open with `<!-- devin-review-comment {json} -->` then `🔍 **<Title>**` | Title emoji wins: 🔴 Critical, 🟠 Major, 🟡 Minor; else `BUG_` id Major, `ANALYSIS_` Minor | The JSON's `file_path`, `start_line`, `end_line`, `side` are the authoritative anchor |
| CodeRabbit (`coderabbitai[bot]`) | Multi-section inline comments with `<details>` | 🔴, 🟠, 🟡; `_⚠️ Potential issue_` alone Major | Skip "Analysis chain" and walkthrough summaries; "Prompt for AI Agents" is fix guidance |
| Gemini Code Assist (`gemini-code-assist[bot]`) | `gstatic.com/codereviewagent/` image URLs | `high-priority.svg` Critical, `medium-` Major, `low-` Minor | Summary opening "Hello @author, I'm Gemini Code Assist!" is not a finding |
| Cursor Bugbot (`cursor[bot]`) | Inline only, no body or verdict | `**High Severity**` Critical, `**Medium**` Major, `**Low**` Minor | "Fix in Cursor" line, `Bugbot Autofix is OFF` footer; an Autofix status comment is not a finding. Re-request with a `bugbot run` comment |
| Copilot (`copilot-pull-request-reviewer[bot]`) | Always `COMMENTED`, never a verdict | None marked: Major, Minor when advisory ("Consider...") | Re-request with `gh pr edit --add-reviewer @copilot` |

Accounting traps:

- Codex usage limit: a body that is only "You have reached your Codex usage limits", no heading, no inline comments. Not a finding, but report once that Codex did not review, so silence is not read as satisfaction.
- Devin: `**Devin Review** found N potential issue(s).` with fewer than N inline threads means the rest are paywalled ("View in Devin Review to see N additional findings"). Report the gap. `## ✅ Devin Review: No Issues Found` with no threads is noise. The `<!-- devin-review-badge-begin -->` block in the PR body is always ignored.
- A bot re-reviewing a new commit opens a fresh thread on the same lines while the old one goes outdated: keep the newest, mark the older `ignore-superseded`.

## Shared identity: github-actions

| Workflow | Detection | Tier and severity |
|----------|-----------|-------------------|
| DangerJS | `DangerID: danger-id-` HTML comment, `data-danger-table="true"`, `Generated by :no_entry_sign: dangerJS` | Active. HTML comment counts: `failure` > 0 Major, `warning` > 0 Minor. Edits one comment in place: compare `updated_at` |
| Schema compatibility checker | Heading with a `.schema.json` filename in `<code>`, `### ⚠️ Warnings` or `### 🔴 Errors`, Field/Type/Status/Details table | Active. `🔴 Error` Major, `🟡 Warning` Minor; `> 💡 **Tip**:` is informational |
| Event-lib RC trigger | Starts "Event-lib RC version is triggered" then a Buildkite URL | Noise |
| Changesets release notice | Starts "This PR was opened by the [Changesets release]", or a `# Releases` heading | Noise |

An `APPROVED` review with an empty body and no inline comments from any automation identity is noise as a finding and evidence that a gate cleared. With inline comments, triage them.

## Merge-gate bots

A comment stating whether the PR may merge is a readiness input. A repo with its own gate bot gets a row here: detection marker, verdict values, what flips the verdict.

**Auto-approval assessment (`linktree-stamp[bot]`).** An issue comment containing `<!-- stamp-assessment -->`, heading `## ✅ Auto-Approval Assessment ([<sha>](...))` or `## 👀 ...`. Edited in place on each commit: compare `updated_at`, and compare the heading SHA with the head SHA to spot a stale assessment.

| `**Verdict:**` | Handling |
|----------------|----------|
| `Auto-approved (LLM assessment)` | Satisfied gate; record it |
| `Human review required` | Blocking gate. Report the `**Path criteria:**` value that forced it |

Carry `**Custom criteria:**`, `**Path criteria:**`, `**Change type:**`, `**Blast radius:**`, and `**Sensitive domains:**` verbatim into the report. `### Reasoning` bullets are context, not findings. A `### <emoji> Path-specific review` section in any colour but 🟢, or with an issue list, is findings at Major. The empty-body `APPROVED` from `developer-platform-actions` follows once the gate clears.

**mergefreeze.** Status only ("Ok to merge"). A freeze blocks merging and is not fixable from code.

## Noise and check-only bots

Match the content marker, not the login: the Linear bot's login already drifted once (from `linear[bot]`) while its marker survived.

| Bot | Detection |
|-----|-----------|
| `linear-code[bot]` | `<!-- linear-linkback -->` |
| `vercel[bot]` | Body starts with `[vc]: #` |
| `renovate[bot]`, `dependabot[bot]` | Author match; dependency descriptions and commands |

Check-only until they comment: Buildkite pipeline checks (`buildkite/{project}/{step}`), telemetry service-attribute validation (`blstrco/telemetry`). A review or inline comment from one promotes it to active reviewer.

## Human review states

An empty human review body is the normal case: the content is in the inline threads. Several empty-body reviews from one person are one review pass.

| Pattern | Severity | Blocking |
|---------|----------|----------|
| `CHANGES_REQUESTED`, with or without body | Major | Yes |
| `COMMENTED` with an inline question, then `APPROVED` seconds later | Minor | No |
| `APPROVED`, empty body, no inline comments | none | No |
| Issue comment, soft ("I'd also...", "up to you") | Minor | No |
| Issue comment, directive ("please use...", "must...") | Major | Depends on review state |

## Severity normalization

| Source | Critical | Major | Minor |
|--------|----------|-------|-------|
| Codex | `P1` | `P2`, no badge | `P3` |
| CodeRabbit | 🔴 | 🟠, lone Potential issue | 🟡 |
| Gemini | high-priority | medium-priority | low-priority |
| Bugbot | High Severity | Medium Severity | Low Severity |
| Devin | 🔴 | 🟠, `BUG_` without emoji | 🟡, `ANALYSIS_`, advisory wording |
| Copilot, unlisted reviewer | none | default | advisory wording |
| Human | "critical", "blocker" | default | "nit", "minor" |

When several sources flag the same issue, use the highest.

## Likely false positives

Bot comments on these are usually wrong: `.md`, `.json`, `.yaml` config (unless security-related), `.lock` files, generated `.sql` migrations, and files headed "auto-generated" or "DO NOT EDIT". Check before fixing; the ignore reason still has to be a legal one.
